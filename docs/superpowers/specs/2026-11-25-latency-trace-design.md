# Трассировка задержки (кнопка «Замеры»)

Дата: 2026-11-25. Статус: на утверждении.

## Зачем

Звук доходит до слушателей за ~1–2 с. Стример в России, LiveKit-сервер (SFU — сервер-ретранслятор) в Нидерландах, слушатели в разных местах. RTT (время круга туда-обратно) РФ↔NL обычно 50–100 мс, поэтому секунды, скорее всего, копятся не в сети, а в буферах (jitter buffer — буфер выравнивания у приёмника, буфер плеера Android) или из-за перехода на TURN/TCP. Нужен инструмент, который со стороны стримера показывает, **на каком участке** уходит время.

## Цели

- Кнопка в `gui_client.py`: 1-е нажатие запускает трассировку, 2-е останавливает.
- Раз в секунду в нижней панели («Ошибки и диагностика») появляется строка с разбивкой по этапам; при остановке — сводка min/avg/max.
- Видно разбивку для каждого подключённого слушателя отдельно.
- Слушатель (веб, Android), пока идёт трассировка, показывает у себя примерную задержку.

## Не цели / анти-цели

- Не меряем односторонний путь и не синхронизируем часы (допущение: туда и обратно одинаково).
- Не меряем «по самому звуку» (метка в аудио) — возможное будущее.
- Не чиним задержку: только измеряем.
- Когда трассировка выключена, она ничего не делает: ни ping, ни опроса статистики; аудиотракт не меняется.
- Только транспорт LiveKit; legacy WebSocket-транспорт не затрагиваем.

## Подходы (рассмотрены)

- **A.** Только статистика стримера: видит лишь участок до сервера. Отвергнут: главный подозреваемый (буфер клиента) не виден.
- **B. Выбран.** Статистика стримера + ping по data channel (канал данных LiveKit) с ответом клиента.
- **C.** Метка в звуке: честнее всего, но сложно и нужна синхронизация часов. Отложен.

## Как работает

Пока трассировка включена, раз в секунду стример:

1. Берёт `room.get_rtc_stats()`: RTT до сервера, jitter, потери. При старте трассировки один раз показывает тип соединения (UDP, TCP или relay через TURN): TCP/relay — частая причина лагов.
2. Шлёт всем data-пакет `topic="lat.ping"`, JSON `{v:1, id, t_sent, pub_rtt_ms}` (`reliable=False`, чтобы ping не стоял в очереди; `t_sent` — монотонные часы стримера).
3. Клиент сразу отвечает адресно стримеру пакетом `topic="lat.pong"`: `{v:1, id, sfu_rtt_ms, jitter_buffer_ms}`. `sfu_rtt_ms` — RTT клиента до сервера, `jitter_buffer_ms` — средняя задержка в его jitter buffer.

Стример считает и пишет в панель:

- `до сервера` = RTT из статистики стримера;
- `круг стример→клиент→стример` = `now − t_sent` по ответу;
- `сервер↔клиент` ≈ круг − до сервера (допущение симметрии);
- `буфер клиента` = `jitter_buffer_ms` из ответа.

Пример строки: `[замер] android-viewer: до сервера 62 мс | сервер↔клиент 85 мс | буфер клиента 940 мс | ≈ 1,0 с`.

**На стороне клиента** (веб и Android): подписка на `lat.ping`, ответ `lat.pong` и показ «≈ pub_rtt/2 + sfu_rtt/2 + jitter_buffer» (это оценка, подпись со знаком «≈»). Если ping не приходят 3 с, показ гасится.

Слушатель без ответа (старая версия) помечается «нет ответа (обновите клиент)»; остальные участки по нему не показываются.

## Что затрагивается

- `gui_client.py`: кнопка, запуск/остановка, вывод в панель. Сейчас `_set_error_log` целиком перезаписывает панель, замеры должны дописываться и не стирать ошибки (и наоборот).
- `livekit_client.py`: старт/стоп трассировки (ping, сбор статистики, приём `lat.pong`), результаты отдаются в UI через существующий `ui_callback`.
- `server.py`: JS веб-страницы слушателя (обработчик data-пакетов, `getStats`, строка с оценкой).
- `android/.../PlaybackService.kt`: обработчик `RoomEvent.DataReceived`, статистика, ответ; показ оценки.
- `docs/architecture.md`: короткий раздел про замеры.

## Мои решения (проверьте)

- Ping раз в секунду, не reliable.
- Кнопка активна только при подключённом стримере; при обрыве связи трассировка останавливается сама.
- Тип соединения показывается один раз при старте.
- Формат пакетов JSON с полем `v:1` на случай развития.

## Оставлено исполнителю

- Точные поля статистики и способ получить jitter buffer на каждой платформе (в Android SDK 2.26.1 и JS-клиенте они отличаются; разбор protobuf-статистики Python SDK проверить на практике).
- Где на Android показывать оценку (уведомление или экран).
- Минимальный тест: чистая функция расчёта «круг − до сервера» и форматирования строки.
